# Umur Emas project memory

## Scope

This file is the durable, repository-local context for agents working on Umur Emas. Keep it concise and factual. Never include secrets or personal data.

## Architecture

- Monorepo: Expo/React Native application in `apps/mobile`, Kotlin/Spring Boot API in `apps/api`, shared domain rules in `packages/core`, UI primitives in `packages/ui`, and typed HTTP client in `packages/api-client`.
- The product name is **Umur Emas**. It supports web, iOS, Android, and tablet layouts.
- PostgreSQL schema changes use incrementing Flyway migrations under `apps/api/src/main/resources/db/migration/`; do not modify an already-applied migration.
- Backend features that persist data require matching service-layer authorization, API route, API-client contract, and migration.

## Product conventions

- When a verified error or bug is found in this repository, fix it directly and verify the repair without waiting for a separate follow-up request, unless the repair requires new external authority or materially expands scope.
- Supported UI languages are Indonesian and English. New visible text belongs in `apps/mobile/src/i18n/translations.ts`; API errors are localized through `Accept-Language` and the API error bundles.
- Any user-flow or business-logic change must update `README.md` in the same change set so the documented behavior remains aligned with the implementation.
- Main role layouts do not use an app bar. Child/detail screens use an app bar and a back button, and do not show the bottom navigation.
- Every operational destination entered from the `STAFF_ADMIN` Kelola hub is a child screen with an app bar and back button; the Kelola hub itself remains a role-level navigation screen.
- `STAFF_ADMIN` accesses Profile from the profile icon in its Home toolbar, not from bottom navigation. Other roles retain their Profile bottom-navigation entry.
- React Native screen and navigation components obtain navigation through Expo Router's `useRouter()` hook; do not import the global `router`, because it is unavailable during this Android runtime's render lifecycle.
- Auth-protected screens must render no redirect while the asynchronously restored `profile` is `null`; apply their role redirect only after that profile has loaded.
- Do not use inline React Native styles. Reuse `@daycare/ui` and local `StyleSheet` definitions. Use `BottomSheet` for a short form with only a few fields; use a dedicated child screen with app bar/back navigation for a larger or multi-step form.
- Operational add, edit, assignment, and password forms must start from an explicit entry action. Do not render a mutation form immediately on opening its screen; short forms open in `BottomSheet`, while larger workflows use their dedicated screen.
- Roles: platform `ADMIN`; tenant `STAFF_ADMIN`, `STAFF`, and `PARENT`.
- Staff Admin manages children, tenant staff, billing, subscriptions, booking approvals, package templates, discounts/promos, and per-branch booking capacity. Staff accounts are deactivated per tenant rather than deleted; inactive `STAFF` retain read access to assigned children and inactive `STAFF_ADMIN` retain tenant-wide read access, while all mutations require an active membership. The caller and the last active `STAFF_ADMIN` cannot be deactivated. Child management supports child profiles, child programs, and staff assignments with `STAFF`, `NURSE`, or `MISS` responsibilities.
- Creating a tenant provisions one active `STAFF_ADMIN` account. Staff Admins can directly create additional `STAFF_ADMIN` and `STAFF` accounts; Parents continue to use invitations.
- Every self-registration is stored with the global `PARENT` registration role, but has no tenant membership until its paid enrollment is approved by a tenant `STAFF_ADMIN`. The onboarding flow uses `parent_enrollments`, keeps the child pending, and turns the enrollment into an active tenant `PARENT` membership plus guardian link only on approval. A rejected paid enrollment retains its entitlement as credit for a date retry.
- `RegistrationRole.PARENT` is the global self-registration type on `UserProfile`, separate from access roles. Platform Admin access comes from `PlatformAdministrator`; tenant access comes from `Membership.role`. A tenant `PARENT` membership is only a tenant-scoped access link. One Parent may have children and active Parent memberships in multiple tenants; every child, enrollment, invoice, entitlement, and operational record remains scoped to its own tenant. The Parent onboarding screen is also the tenant switcher and entry point for an application to an additional tenant; its new-enrollment selector excludes tenants where that Parent is already active.
- Parent attendance QR payloads include the child ID and name, and their short-lived server token is signed against both values; the scan flow trusts the signed token, not the display name alone.
- Parent self-enrollment is finalized only through the Staff Admin enrollment decision shown in Booking Approvals; linked ordinary booking rows cannot bypass activation. Enrollment checkout purchases a package without creating a booking or reservation; booking capacity is checked and reserved only after Parent–tenant binding is active. Expired unpaid applications become `EXPIRED`, and a pending Parent screen refreshes the profile after approval.
- A Parent can cancel only an unpaid (`PENDING_PAYMENT`) enrollment. Cancellation voids its invoice and expires the associated entitlement; paid applications remain governed by Staff Admin approval or rejection. Notifications are delivered through Expo on registered native devices and are also available to every tenant role in the Profile inbox; read state is persisted per recipient.
- Learning structure is tenant-generic: `LearningLevel` (for example Nursery, Toddler, PAUD, TK A, TK B) is separate from a parallel `Classroom`/rombel. A classroom may have its own named programs, distinct from tenant curriculum programs linked to a level. `ChildPlacement` preserves history with one active placement, and Staff may manage children assigned directly or through an active classroom assignment. Learning periods are optional for every institution type; templates are filtered by institution type but tenant-defined levels remain allowed.
- Platform Admin may create global curriculum programs. They have no tenant owner, are listed alongside a tenant's own curriculum programs, and can be linked directly to that tenant's learning levels without copying or letting tenants alter the global definition.
- Staff may approve ordinary bookings and place children only inside their direct or active classroom assignment scope. Parent enrollment binding remains a Staff Admin-only decision. Inactive Staff Admin accounts retain only read UI and inactive Staff accounts retain only scoped read UI.
- `STAFF_ADMIN` can grant an active `STAFF` a per-tenant child-program permission from Tenant Accounts. It defaults to disabled and permits adding or removing a child's programs only within that Staff member's direct or active classroom assignment scope.
- Tenant is the data and billing boundary; a tenant may own multiple active branches but exactly one primary branch. `STAFF_ADMIN` manages its tenant's branch lifecycle; Platform Admin has read-only branch visibility for support plus tenant billing and subscription control. Adding a branch never creates another Staff Admin account: `STAFF_ADMIN` membership remains tenant-wide, and inactive branches are excluded from new enrollment, child, class, and capacity flows.
- `apps/mobile/src/audio` is a generic Android/iOS-only, foreground recording module. It produces temporary M4A cache files for at most five minutes; callers own upload, persistence, and deletion. It has no screen or API wiring.
- `apps/mobile/src/image-picker` is a generic Android/iOS-only picker for up to ten compressed gallery images or one camera image. It has no crop UI, storage, upload, API, or screen wiring; callers own persistence and upload.
- Local-only authentication is enabled only with `LOCAL_AUTH_ENABLED=true`; it uses a locally seeded PostgreSQL account and an HMAC JWT, while Firebase authentication remains the development and production path.
- The local mobile launcher owns the API process and stops it on exit. For a connected Android device, the local launcher uses `adb reverse` for ports `8080` and `8081` and runs Expo on localhost, avoiding Wi-Fi routing dependencies. Network failures during tenant creation must be handled without an automatic retry, because the server could have completed the request before the client lost its response; the user checks the tenant list first.
- The root Expo Router stack starts at Home through `initialRouteName`; do not imperatively redirect from the root layout before its navigation container is ready. Any root-level navigation effect must check `navigationRef.current?.isReady()` first.
- Realtime uses the native `/api/v1/realtime` WebSocket endpoint. Clients authenticate with their JWT in the first `CONNECT` frame, receive tenant-scoped generic events with multiple invalidation flags, and reload REST/React Query data; websocket payloads are never the source of truth.
- The STAFF_ADMIN Children list supports cascading tenant-scoped filters: branch, then learning level, then active classroom/rombel. Filter selections are draft-only until the user presses OK; closing the sheet discards draft changes. The backend validates every supplied identifier and their hierarchy after applying the caller's existing child scope, so filters only narrow access and never expand it.
- Child records retain a gender value. New Staff Admin child creation, Parent enrollment, and child-profile updates require a Male or Female choice; existing records migrated before this field use `UNSPECIFIED` until a Staff Admin updates them.
- Goals are a separate development module, not a curriculum program or learning level. `STAFF_ADMIN` creates scoped Goal templates for a learning level and optionally a classroom, then assigns one active instance of a template to a child. Active-goal progress always reflects the current template targets. Staff Admin and active Staff record or amend one Yes/No result per in-period day for children within their scope, and may finalize an active Goal manually as achieved or not achieved with a required summary. Missing days are excluded from the Yes percentage but break a consecutive-Yes streak. Parents can only read their linked child’s daily results, calculated progress, and final summary.

## Verification

- TypeScript/mobile: `corepack pnpm verify`.
- Spring API: set JDK 21, then run `gradle -p apps/api test --no-daemon`.
- API tests include unit tests and a Spring integration baseline. The integration test uses local JWT authentication plus PostgreSQL/Flyway from `INTEGRATION_DATABASE_URL`, `INTEGRATION_DATABASE_USERNAME`, and `INTEGRATION_DATABASE_PASSWORD`; it never uses Docker and is skipped when the dedicated local test database is not configured.
- The local PostgreSQL database may be launched with Docker Compose when Docker is installed; it is not bundled in the repository.
